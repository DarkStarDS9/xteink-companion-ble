# Multi-App / Multi-Phone Companion Platform — Design

**STATUS: adopted as protocol v6.** This is the platform base the Polaroid roadmap item (and
everything after it) needs. The authoritative wire contract is now
`docs/companion-display-protocol.md` v6; this document is the reasoning behind it and stays the
place to look for *why*, not *what*. Where the two differ, the protocol doc wins. §12 records how
this design's open questions were closed and which wire decisions were added beyond §9.

Everything here follows the fork's guiding principle: **dumb firmware, smart phone**. The device
stores per-app state and renders what it is told; it never interprets what an app or a button
means.

---

## 1. The problem, stated precisely

Three usage shapes are wanted:

| Shape | What it actually requires |
|---|---|
| One phone, multiple apps → one device | **Session multiplexing.** See §2 — this is the hard one. |
| Multiple phones, multiple apps → one device | Enrollment of many peers; one connected at a time. |
| One phone → multiple devices in range | Almost entirely phone-side. Firmware just needs to expose a stable device id. |

And the storage requirement: **each phone:app combination gets its own directory on the SD card**,
holding metadata — button labels, whether a button is handled on-device or forwarded, an icon.

## 2. The load-bearing constraint: BLE cannot tell two apps apart

A BLE peripheral has **one link per central *device*, not per app**. When two apps on the same
phone connect to the same peripheral, the OS shares a single underlying connection — the peripheral
sees one connection handle, and writes from both apps arrive interleaved on the same
characteristics with nothing distinguishing them.
([Punch Through's Core Bluetooth guide](https://punchthrough.com/core-bluetooth-guide/) covers the
iOS side of this; the same is true of Android.)

The consequence is not subtle. Under v5 framing, if SpokenFeeds and the camera app are both open
and both push content, their `START`/`CHUNK`/`END` frames interleave into one reassembly buffer and
produce garbage. There is no link-layer fix.

**So app identity must be declared in-band.** That single fact is what forces a session layer, and
it is required even though we only ever hold one BLE connection. Sessions are not about multiple
phones — they are about multiple apps on *one* phone.

## 3. Identity model

Three ids, all opaque to the firmware:

- **`appId`** — 16 bytes, chosen once by the app author, identical across every install of that
  app. Identifies *which app*. Drives icon grouping.
- **`installId`** — 16 bytes, random, generated by the app on first run. Identifies *which phone's
  copy*. Two phones running the same app are two peers with one shared `appId`.
- **`deviceId`** — 4 bytes, the eFuse MAC tail already used in the advertised name. Exposed in the
  capability characteristic so the phone can key *its* storage per device.

A **peer** is the pair `(appId, installId)` — exactly the "phone:app combination" from the
requirement. Its directory name is `peerKey`, the first 8 hex chars of a hash over both ids.

The firmware never parses or validates these beyond byte equality. An app that regenerates its
`installId` simply becomes a new peer and re-pairs.

## 4. Storage layout

```
/.crosspoint/companion/
  peers.json                     index: peerKey -> { appId, installId, displayName, lastSeenMs }
  peers/<peerKey>/
    peer.json                    display name, auth token, protocol prefs
    icon.bin                     1-bpp sleep-screen icon
    buttons.json                 button map (labels + routing) — see §7
    data/                        scratch: the in-flight image transfer only
    images.json                  gallery index: slot -> seq, content-id
    images/                      up to kMaxImagesPerPeer (6) stored pushes, img_<slot>.raw
```

Consistent with the existing `/.crosspoint/` convention (`settings.json`, `state.json`,
`bookmarks/`, `epub_<hash>/`). `peers.json`, `peer.json`, `buttons.json` and `images.json` go
through the existing `PersistableStore`; `icon.bin`, `data/` and `images/` are raw `HalStorage`
files.

`data/` is the answer to "where does the Polaroid staging file go" — per-peer rather than a single
global `incoming_image.png`, so two apps staging at once cannot collide.

**Images are not single-shot anymore.** A push completes into `data/incoming.raw` as before, but
once whole, `CompanionPeerStore::commitImage()` renames it into a bounded per-peer gallery
(`images/`, `kMaxImagesPerPeer` slots reused oldest-first, indexed by `images.json`) instead of
leaving one scratch file that the next push would silently overwrite. `CompanionModeActivity` browses
that gallery with `Button::Up`/`Down` — the side buttons, not `Left`/`Right`: on real hardware those
are the bottom front buttons, and every button map seen so far routes them to local text paging, so
`Up`/`Down` are the pair actually free for this (see `MappedInputManager.h`) — while `Screen::Image`
is showing, and only on whichever of those two buttons the foreground peer's own button map has left unclaimed
(routing `None` or `LocalPagePrev`/`LocalPageNext`, which is already a no-op outside `Screen::Text`);
a peer that declared its own use for Up/Down (e.g. `Remote`, for something like camera control) is
never overridden. This is deliberately **firmware-local**: no protocol opcode, no capability bit, nothing
reported to the phone, exactly like the existing `currentPage`/`totalPages` text pagination that
`LocalPagePrev`/`LocalPageNext` already drive with no BLE notification. Six images per peer costs
~612 KB of SD space at the measured panel's ~102 KB/image (trivial against a multi-GB card) and no
RAM: only one image is ever decoded into the framebuffer at a time, same as before this feature.

## 5. Pairing / enrollment

**Decided: app-level token over an unencrypted link.** No BLE bonding. The token is a capability to
skip the on-device confirm prompt, not a secrecy mechanism — it works identically on iOS and
Android and avoids the OS re-pairing failure modes that bonding brings.

**This means the link is sniffable.** Acceptable for photos and article text; it is *not* a
foundation for anything confidential. If that changes, LE Secure Connections is the upgrade, and §12
notes what it would cost.

Flow:

1. Central connects, writes `HELLO` on the Session characteristic with `appId`, `installId`,
   display name, and a token if it has one.
2. **Unknown peer, or bad token** → device prompts on screen: *"Pair with <name>? CONFIRM / BACK"*.
   The device notifies `HELLO_PENDING` so the app can show "confirm on your device".
   - Confirmed → device creates `peers/<peerKey>/`, generates a random 16-byte token, replies
     `HELLO_OK` carrying the token and the assigned `sessionId`. The app stores the token.
   - Rejected, or no input within a timeout → `HELLO_DENIED`.
3. **Known peer with a valid token** → immediate `HELLO_OK`, no prompt. This is the "can connect
   automatically" relationship.

**Enrollment is not complete until the app's assets arrive.** `HELLO_OK` carries an **asset digest
block** — for each per-peer asset, the opaque 4-byte tag the device currently has stored, or zero if
it has none:

```
assetCount : 1
assetCount × { assetId : 1, tag : 4 }      assetId 0x05 button map, 0x06 icon
```

The app compares each tag against its own and pushes any asset whose tag differs — as content field
`0x05` / `0x06`, each prefixed with its 4-byte tag, which the device stores verbatim alongside it.

This is deliberately inverted from "app sends a hash, device says stale or not". The device performs
no comparison and computes no hash; it stores opaque bytes an app handed it and reads them back.
Which asset is stale is the app's conclusion, not the firmware's.

The tag is opaque to the firmware, so an app *may* use a counter — but a content hash is
recommended. A counter breaks on app downgrade, where the device holds a tag the older build will
never produce again; a hash is correct in both directions.

**A peer with no button map cannot take the screen.** `ACQUIRE` is rejected until one is stored. See
§7 — this makes an app with undefined buttons structurally impossible rather than a case the
rendering code has to handle.

Unpairing is on-device only (delete the peer directory). No protocol opcode — an app that wants to
be forgotten is not a case worth wire surface.

## 6. Sessions and screen ownership

There is one screen, so exactly one session is **foreground** at a time. Everything else is
background.

- The device assigns a `sessionId` (1 byte) in `HELLO_OK`. Every content frame carries it.
- **Only the foreground session may push content or receive button events.** Frames from a
  background session are dropped.
- An app requests the screen with `ACQUIRE`. Policy is **last requester wins, unconditionally** —
  the user just brought that app to the foreground on their phone, and arbitration is phone-side
  knowledge the firmware does not have. Dumb firmware.
- The preempted session gets a `BACKGROUND` notification so it can stop pushing.

**Switching apps on the phone is not a firmware mode change** — exactly as intended. The new app
sends `HELLO` (auto-accepted) then `ACQUIRE`; the device loads that peer's button map, clears the
screen, and renders whatever the new session pushes. Same protocol, same activity, different data.

Session cap: 4. Only the foreground session has a reassembly buffer, so the number of large buffers
is unchanged from today.

**Decided: the device retains no content for a background session.** On reacquiring the foreground,
an app re-pushes. The alternative — buffering per-session content so switching back is instant —
costs one reassembly buffer per session on a part with no room for a second one, and violates §2 of
`SCOPE.md` ("the device holds no state the phone cannot reconstruct").

## 7. Button map — labels and routing

The requirement from the pairing metadata: *"button labels; does button A trigger internal
functionality or send something to the phone"*.

**Mandatory, from registration onward.** A peer supplies its button map during enrollment, and
re-supplies it on any connect where its tag has changed (§5). There is no unmapped peer state: the
device rejects `ACQUIRE` from a peer with no stored map. An app therefore cannot reach the screen
without having declared what its buttons do.

Pushed as content field `0x05`, persisted to `buttons.json` in the peer directory so it survives
reconnect and can still be rendered while disconnected — which is what lets the sleep screen and the
"waiting for <app>" screen show correct hints with nothing connected.

```
bytes 0..3: asset tag (opaque, stored verbatim — see §5)
byte 4:  entry count N
N × {  buttonId : 1
       routing  : 1
       labelLen : 1
       label    : labelLen bytes, UTF-8, may be empty  }
```

`routing` is a small **closed** enum — this is the entire set of things the firmware can do by
itself, and it stays closed on purpose:

```
0x00  NONE               no hint drawn, no notification — button is dead in this app
0x01  REMOTE             notify the phone (raw button id + hold duration, exactly as v5)
0x02  LOCAL_PAGE_PREV    page the locally-buffered body backward
0x03  LOCAL_PAGE_NEXT    page the locally-buffered body forward
0x04  LOCAL_SLEEP        sleep the device
```

Notes:

- `POWER` is **not remappable**. It stays firmware-owned in every app.
- The label is an opaque string the firmware only draws. It carries no meaning to the device — a
  `REMOTE` button labelled "Shutter" is still just "notify raw button id 1".
- There is **no default map for a peer.** The v5 fallback (LEFT/RIGHT page locally, everything else
  notifies) does not survive as an implicit default — an app declares its scheme or does not get the
  screen. The firmware keeps its own fixed scheme only for its own screens: pairing confirmation,
  "waiting for <app>", and the sleep grid.
- **App updates are the reason this is versioned rather than push-once.** A new app build that adds
  a feature ships a new button map with a new tag; the device picks it up on the next connect
  without re-pairing, and without the app having to track whether it already pushed.
- This is what makes per-app control schemes work without a firmware mode: a photo-viewing app
  labels UP/DOWN "Prev"/"Next photo", a reader labels CONFIRM "Save". Same firmware, same buttons,
  different strings and routing.

## 8. Sleep screen — installed-app icons

**Decided: pushed bitmaps, decorative.** Each peer uploads a 1-bpp icon (content field `0x06`,
fixed dimensions advertised in the capability characteristic — 64×64 = 512 bytes proposed), tagged
and refreshed through the same asset-digest mechanism as the button map (§5) — so an app that
redesigns its icon ships it in an update and the device picks it up on the next connect. The
sleep screen draws a grid of every enrolled app, **grouped by `appId`**, so the same app paired
from two phones is one tile, not two. The currently-connected app's tile is marked.

Not a launcher. The device cannot start an app on the phone, so a selectable grid would promise
something it can't deliver; the payoff would be a hint to an already-backgrounded app, which is not
worth the UI. Revisit only if a real mechanism appears.

Icons are read from SD one at a time into a 512-byte stack buffer at render, drawn, and discarded.
None are resident.

## 9. Wire format changes (v6)

**Decided: clean break.** The handshake is mandatory — a client that pushes content without a valid
session is rejected. No legacy anonymous-session path.

**Release coordination cost, stated plainly:** flashing v6 firmware breaks the shipped SpokenFeeds
build until it ships a v6 update. Both sides must be released together.

### Content characteristic framing

`sessionId` is added to **every** frame, not just `START`:

```
START:  byte 0 = 0x01 | byte 1 = field|final | byte 2 = sessionId | bytes 3..4 = total len (u16 LE)
CHUNK:  byte 0 = 0x02 | byte 1 = sessionId   | bytes 2..N = payload
END:    byte 0 = 0x03 | byte 1 = sessionId
```

Putting it on `CHUNK` too costs one byte per packet. It is worth it: without it, a stray write from
a buggy background app is silently attributed to the in-flight transfer and injects bytes into
another app's content. The apps here are cooperating, not adversarial — but they are written by
different codebases on different release cycles, which is the same failure mode.

### New Session characteristic

```
7c9c0005-3e4a-4b1a-9c1e-6d8a1f2b0001   (Write, Notify)
```

Phone → device:

```
0x01 HELLO     appId[16] installId[16] tokenLen:1 token[..] nameLen:1 name[..]
0x02 BYE       sessionId
0x03 ACQUIRE   sessionId
0x04 RELEASE   sessionId
```

Device → phone (notify):

```
0x81 HELLO_OK       sessionId, token[16], assetCount:1, assetCount × { assetId:1, tag[4] }
                    tag is all-zero when the device holds no copy of that asset. See §5.
0x82 HELLO_PENDING  (awaiting on-device confirmation)
0x83 HELLO_DENIED   reason
0x84 FOREGROUND     sessionId
0x85 BACKGROUND     sessionId, reason (0 preempted / 1 released / 2 link lost)
```

### Field id allocation

`0x01` title, `0x02` body, `0x03` content-id, **`0x04` image**, **`0x05` button map**,
**`0x06` icon**. Next free: `0x07`.

### Capability characteristic (v6)

```
byte 0       protocol version = 6
byte 1       screen width in characters
byte 2       screen height in characters
bytes 3..4   max content length, u16 LE (title/body)
byte 5       feature flags: bit0 image, bit1 button map, bit2 icons, bit3 sessions
bytes 6..7   max image length, u16 LE
byte 8       max concurrent sessions
byte 9       icon width in pixels
byte 10      icon height in pixels
bytes 11..14 deviceId (eFuse MAC tail)
```

## 10. "One phone, multiple devices" — deliberately almost nothing

This shape needs no session or storage work. The phone stores `deviceId → its own peer state` and
matches devices by the advertised name suffix (already a MAC tail) or the platform's peripheral
identifier. The only firmware contribution is exposing `deviceId` in the capability characteristic,
above.

Called out explicitly so it does not get over-built. Nothing else here is for it.

## 11. Memory answer (required by `SCOPE.md` §3)

| Item | Where it lives | Cost |
|---|---|---|
| Peer records, icons, button maps | SD | 0 RAM |
| Session table (4 × ~40 B) | RAM | ~160 B |
| Foreground peer's button map + name | RAM | ~150 B |
| Icon render buffer | stack, transient | 512 B |
| Content reassembly | unchanged — foreground only | no change |
| Image staging | streamed to `peers/<peerKey>/data/`, per the image sketch | no change |
| Image gallery (up to 6/peer) | SD (`peers/<peerKey>/images/` + `images.json`) | 0 RAM |
| Gallery nav state (path list + index) | RAM, foreground peer only | ~200 B (6 × short path) |

Net new steady-state RAM: **under 1 KB.** No new large allocation, which is what §3 actually asks.
The design deliberately pushes every per-app structure to SD for this reason.

## 12. Open questions — resolved

All five were closed during the v6 implementation. Resolutions below; the wire-visible ones are
written up in `docs/companion-display-protocol.md`, which is authoritative.

- **What is on screen when the foreground app disconnects?** **Resolved: hold the last content**,
  then fall through to the sleep/icon screen on the existing 5-minute idle timeout. No blanking on
  disconnect — a photo stays a photo and an article stays readable after the phone walks away, which
  is the whole point of an e-ink second screen. Blanking would also make a brief BLE dropout look
  like a device fault.
- **Icon dimensions.** **Resolved: 64×64, 1-bpp, 512 bytes.** On the measured panel (528×792 — see
  below) that tiles as 6 × 3 = 18 with comfortable gutters, which is well past any plausible number
  of paired apps.
- **Token replay.** **Resolved: accepted**, as §5 anticipated. Restated in the protocol doc as an
  explicit "do not push anything confidential over this protocol" so it cannot be missed by a
  client author.
- **Enrolled-peer ceiling.** **Resolved: 32 stored peers, LRU-evicted by `lastSeenMs`; 18 drawn.**
  A display cap alone is not enough — `peers.json` is parsed into RAM, so unbounded storage is an
  unbounded allocation, which §11 forbids. 32 peers is ~2 KB of JSON.
- **`upstream/feat-bluetooth` collision.** **Resolved: no collision today.** That branch has not
  merged to `develop`; the fork carries no BLE central role. If it ever merges, the conflict is
  NimBLE init/teardown ownership, not the session layer.

### Wire decisions made during implementation, beyond §9

Each is argued in place in the protocol doc; listed here so §9 is not read as complete.

- **`helloTag`** — a 2-byte client nonce on `HELLO`, echoed on all three `HELLO_*` replies. Without
  it, two apps handshaking concurrently on one link cannot tell whose `HELLO_OK` is whose: they have
  no `sessionId` yet, and notifications reach both. Same class of problem as §9's argument for
  `sessionId` on `CHUNK`.
- **`ACQUIRE_DENIED` (0x86)** — §5 gates `ACQUIRE` on a stored button map but gave no way to say so.
  A silent rejection would strand an app with no idea why nothing renders.
- **`ASSET_ACK` (0x87) and `IMAGE_STATUS` (0x88)** — whether an asset stored and whether an image
  decoded are the two outcomes a phone genuinely cannot reconstruct. Everything else about rendering
  follows deterministically from what was pushed.
- **START length widened to uint32.** §9 kept v5's uint16, which caps a push at 65,535 bytes — too
  close to a real dithered full-panel grayscale PNG for comfort. Two bytes per START, once per field,
  removes the ceiling entirely; the actual cap is now `kMaxImageFieldLen` and SD space.
- **`sessionId` on button events and Status writes.** §9 covered the content direction only.
  Notifications are delivered to every app on the shared link, so the reverse direction has the same
  ambiguity and needs the same tag.
- **Capability block additions** — screen pixel dimensions (an image pusher must know the target
  canvas), max content-id length, and grey-level count. The block is 23 bytes.

### Panel size: measured, not assumed

An X3 in Companion Mode reports **528 x 792** pixels with a **52,272-byte** framebuffer, read off
the live renderer and confirmed against `display.getBufferSize()`. Several inherited notes in this
repo (and this document's own first draft) say 800 x 480 / 48,000 bytes; that is wrong for this
hardware. Nothing should hardcode either number — the capability characteristic carries the live
value for exactly this reason.

## 13. Sequencing

Phase A and B are what the Polaroid item actually blocks on.

- **A — Sessions, enrollment, peer storage, button map.** §3–§7, §9. The bulk of the work and the
  v6 break. The button map is **inside** phase A, not after it: it is required at registration and
  gates `ACQUIRE`, so there is no coherent intermediate state where sessions work and buttons are
  undefined. The asset-digest mechanism (§5) lands here too, since enrollment depends on it.
- **B — Icons + sleep screen grid.** §8. The one genuinely separable piece: the icon is a second
  asset riding mechanism that already exists after A, and nothing blocks on the grid. Can slip.
- **C — Image push.** `docs/companion-image-protocol-sketch.md`, landing on a base that already
  provides per-peer staging (§4) and declared button labels (§7). Two of that sketch's open
  questions — where the staging file lives, and the on-device UI/mode for "image mode" — are
  answered by this document rather than needing their own mechanism. Needs A; does not need B.

## 14. Prior art reviewed

`ROADMAP.md` flagged two CrossPoint forks as prerequisites to read. Both were reviewed; verdict:
**the shape transfers, the mechanism does not.**

- [`zakerytclarke/crosspoint-reader-apps`](https://github.com/zakerytclarke/crosspoint-reader-apps)
  has a real framework: `src/activities/App.h` defines an app as
  `{ NameGetter, UIIcon, Factory, VisibleCallback }`, and `AppRegistry` is a singleton holding a
  `std::vector<std::unique_ptr<App>>` populated in its constructor. Entry is "instantiate the
  Activity"; exit is the normal `ActivityResult` path. There is no per-app storage abstraction and
  no dynamic registration.
- [`0x1abin/crossmux`](https://github.com/0x1abin/crossmux) is an Apps-hub menu (games, tools,
  standby faces) with page-dot pagination once apps overflow a screen. Apps are hardcoded per build
  environment. It caches aggressively under `.crosspoint/` for the same RAM reasons we do.

**Why neither is adoptable:** both register *on-device* apps at compile time and enter them by
constructing an `Activity`. Our apps live on the phone, are registered at *runtime* by pairing, and
never produce an on-device activity — the companion activity is the only one, and it just renders
different data. A compile-time registry cannot express "an app that was paired yesterday".

**What was taken:** the registry record shape — `{ stable id, display name, icon, visible }` — is
essentially §3 plus §8, and `AppRegistry`'s job is done here by `peers.json`. The paginated icon
grid is the right model for §8's sleep screen. The `.crosspoint/` per-app cache-directory
convention is what §4 extends.

Recorded here so the "should we adopt one of these" question does not get re-opened; see
`SCOPE.md` §6 for the same treatment of the base-repo question.
